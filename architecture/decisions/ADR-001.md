# ADR-001: Three model roles, and a script for release

- **Status:** Accepted. The role split ran on every finished issue, including [run 44799110233](https://github.com/Anilkumark17/tinydb/actions/runs/44799110233). The model names in the table were superseded by ADR-014 and ADR-015.
- **Date:** 2026-11-20

## Context

The assignment has six stages and asks how I split them. One agent could hold the issue, the spec, the diff, the pytest log and the review in one chat. Six agents, one per stage, would read the repo again every time. The reviewer has to be separate from the person who wrote the code, so that cut is required.

The TinyDB changes here are small. Issue 1 is a doc-id check in `Table.update` and `Table.remove`. Planning reads the same files that coding edits. Release pushes a branch and opens a pull request. I already know the base branch and where the title comes from.

## Decision

Four roles:

| Role | Stages | Model |
| --- | --- | --- |
| Analyst | 1 Requirements, 2 Design | `gemini-2.5-flash` |
| Implementer | 3 Implementation | `gemini-2.5-flash` |
| Tester | 4 Testing | `gemini-2.5-flash` |
| Reviewer | 6 Review | `gemini-2.5-pro` |

Stage 5 is a script. It does not call a model.

The analyst stays one process for stages 1 and 2. Both are read-only, and the design is the spec made concrete. The stage 1 script has to pass before it writes `design.md`.

The implementer and the tester are different processes. The tester writes tests from `spec.md`. It gets the diff, and on a retry the pytest log. It does not get the implementer's messages. One process that both edits `tinydb/` and writes the tests can make the tests match whatever it already wrote.

## Alternatives considered

One agent for all six stages. The review would sit in the same chat as the implementation. ADR-008 is there to stop that. A retry of stage 3 would also resend the whole history.

One agent per stage, six model calls. Stages 1 and 2 would both re-read `ARCHITECTURE.md` and the issue. The only new input to stage 2 is `spec.md`, which the analyst just wrote. I don't need that extra call until the reviewer.

An agent for release. It would pick the base branch, the title and the `gh` arguments. The base has to be `master` or `ci-workflow.yml` does not run. A script that takes the title from the first heading of `spec.md` and calls `gh pr create --body-file` cannot retarget the pull request or merge it.

## Consequences

A test failure goes back to the implementer as a log, not as a memory of why the edit was written. If the log is thin, it can repeat a bad edit. The retry budget in ADR-009 stops that loop.

Release cannot write a pull-request body that hides a failing test. The body is the spec's acceptance criteria plus the link to `test_report.md`. The script will not push when pytest's exit code is non-zero.

The reviewer was the only role on `gemini-2.5-pro`. The cost of that split is in ADR-006. Those model ids did not last.
