# ADR-016: Stage 5 fails on a CI regression, not on a CI that is already red

- **Status:** Accepted. Supersedes the CI condition in ADR-007 (stage 5). Learned from a real run.
- **Date:** 2026-11-20

## Context

ADR-007 says stage 5 passes when the `ci-workflow` check on the pull request succeeds. The first real run on issue #1 opened pull request #12. The review never ran, because stage 5 failed on CI.

The Actions list for the fork shows that `Python CI` failed on every run, including pushes to `master` and `a3-design` that contain no agent code: runs #1 to #14. The same 18 jobs (build matrix plus the coveralls job) are listed on pull request #12. I had not read the failing logs yet. Two candidates in `ci-workflow.yml` were the `pypy-3.9` leg, while `pyproject.toml` requires Python 3.10 or later, and the coveralls upload, which needs a coveralls.io registration a fork does not have. Neither was confirmed at the time. ADR-019 later found the real cause.

Whatever the cause, a CI that is red on `master` makes "the CI check succeeds" impossible for every pull request, no matter what the agent wrote. The check then measures the fork, not the change.

## Decision

Stage 5 compares the pull request to the base branch. Before it pushes, the release step reads the job names that failed in the latest completed `Python CI` run on `master`. It waits until no check on the pull request is pending. It fails only if a job is red on the pull request and was not red on `master`. The check passes with a note in `pr.md` that says how many checks also fail on `master`.

I do not edit the project's CI file here. The fork's own CI problem is a known limitation. If it gets fixed, a person does that in a separate pull request.

## Alternatives considered

Edit `ci-workflow.yml` to drop `pypy-3.9` and the coveralls steps. The check keeps its original meaning, but it changes the project's own CI file, and the cause was not confirmed.

Drop the CI condition from stage 5. The assignment's check for stage 5 includes that CI passes.

Run only the jobs for one Python version. That narrows the check to something that passes today, and it is a hand-picked subset.

## Consequences

A real regression in a job that is green on `master` still stops the run. A regression in a job that is already red on `master` is not seen by stage 5. Stage 4 runs the full local suite, and the reviewer can call `run_tests`. That covers tests. It does not cover the type check or the build check.

The baseline is the latest completed run on `master`, which can be older than the base commit of the pull request. If `master` moved, the baseline can be stale.
