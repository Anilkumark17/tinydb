# ADR-004: Artifacts hold run state, the branch holds code

- **Status:** Accepted. Stage artifacts were uploaded on the finished runs and were not committed onto the pull-request branches.
- **Date:** 2026-11-20

## Context

A later job on a later runner cannot see the previous job's disk. GitHub has three stores that matter here: files committed on the branch, workflow artifacts, and the Actions cache. Pull-request comments are a fourth store. People can read them, and so can any later step that trusts them.

`master` is protected. A direct push to `master` is rejected. The workflow may push a new branch and open a pull request. It may not merge.

The five issues can be started twice, by a label and by a comment, or by two clicks. A restarted run must not mix a new issue body with an old spec.

## Decision

| Store | What goes there | What does not |
| --- | --- | --- |
| Actions artifacts, one per stage | `spec.md`, `design.md`, `diff.patch`, `test_report.md`, `pr.md`, `review.md`, and `state.json` | Secrets, the Gemini key, raw model transcripts |
| The feature branch `autose/issue-<n>` | The source edit and the tests under `tests/` | Spec, design, review, transcripts |
| Pull request | The url, recorded in `pr.md`, and the review comment posted from `review.md` | The only copy of a stage artifact |
| Actions cache | Nothing for this workflow | Dependencies are installed by `uv sync` in the job. Caching them is an optimisation for later, not state. |

`state.json` holds the issue number, the branch name, the pytest attempt count, the design-return count and the review round. The next job downloads the artifacts by name. It does not scrape the log.

A re-run starts at stage 1. It does not download artifacts from an older run id. The issue may have been edited. An old spec would hide that edit.

Concurrency is one in-progress run per issue number. A second trigger waits. It does not cancel the first run. Cancelling mid-push can leave `autose/issue-<n>` updated and the pull request missing.

## Alternatives considered

Commit every artifact onto the branch. A person reading the pull request would see the spec beside the code, and a restarted job would not need artifacts. The reviewer checkout would then contain `spec.md` and `design.md`, which breaks ADR-003. The branch would also contain the analyst's words in a commit I am asked to merge.

Store state in pull-request comments and parse it back. Comments are easy to read and easy to edit. The next run would be one edited comment away from `attempt=0` or `verdict=approve`.

Use the Actions cache as the hand-off. The cache is for dependency reuse, it can be evicted, and it is shared more widely than a named artifact of one run. Wrong lifetime for a spec.

## Consequences

A failed run still leaves its artifacts, which is what the assignment wants: a person can follow the run from the artifacts and the pull request. A failure before stage 5 leaves no pull request. The artifacts are the whole record in that case.

`state.json` can drift from the real pytest exit code if a job writes it by hand. The builder writes `attempt` only after pytest returns, and stores the exit code in the same file. The release job reads that exit code and will not push on a non-zero value, even if the prose report says the tests passed.

Waiting rather than cancelling means two clicks on the same issue run one after another and cost two analyst calls. That is the cost of not interleaving two pushes to `autose/issue-<n>`.
