# ADR-006: Flash writes the change, Pro reviews it

- **Status:** Superseded by ADR-014. The first Actions run returned HTTP 404 for `gemini-2.5-flash`.
- **Date:** 2026-11-20

## Context

I have one Gemini key. A model-list call on that key returned `gemini-2.5-flash` and `gemini-2.5-pro`, among others. There is no second provider key, so I cannot put the reviewer on another vendor without a new secret.

The assignment allows one model for every role. It also says a different model for the reviewer is worth thinking about, because a reviewer that shares the author's blind spots will agree with it.

Flash is the cheaper and faster of the two. A full run is one analyst call, one or more implementer calls, one or more tester calls, and one or two reviewer calls. The coding calls are most of the count. The review calls are the ones that have to be willing to disagree.

These TinyDB issues are local edits to `Table`. They do not need the larger model to find `table.py`. They need a careful reader at the end, looking at a diff it did not write.

## Decision

| Role | Model | Why this one |
| --- | --- | --- |
| Analyst, implementer, tester | `gemini-2.5-flash` | Several calls per issue. The stage checks are scripts and pytest, so a weak patch fails even when the model is sure. |
| Reviewer | `gemini-2.5-pro` | One or two calls per issue. A larger model, a different prompt, and a context that leaves out the builder's notes. |

Temperature stays at the provider default. I do not change it between roles. Changing it would make two runs harder to compare, and it would not separate the reviewer from the builder.

No run uses a preview or TTS model from the same key. The model id is fixed in the runner. It is not chosen from the issue text.

## Alternatives considered

Pro for every role. The review would be stronger, and so would the bill. Five issues, with retries, on Pro is the wrong default under a small monthly cap. Stages 1 to 5 do not need the larger model in order to fail a bad patch.

Flash for the reviewer as well. One model id is simpler, and the permission split in ADR-008 would still hold. The reviewer would share Flash's mistakes. The only independence left would be the empty context. ADR-008 keeps that empty context either way. This ADR adds a second model id on top of it.

A second provider for the reviewer. That is the stronger experiment. It needs a second secret I did not have. If one is added later, this ADR should be superseded, not edited in place.

## Consequences

A Flash implementer and a Pro reviewer can still share training data and still both miss a TinyDB rule. The model change cuts same-model agreement. It does not make an independent implementation.

The runner has to send the model id. If the id is left out, the provider's default might be Flash for the reviewer too, and this ADR would be void without anyone noticing. The review job fails closed when the response does not identify `gemini-2.5-pro`.

Cost is reported later as token counts from the runner, not estimated here. This record only says which model is allowed to spend those tokens.
