# ADR-002: A fixed Actions pipeline decides the back-edges

- **Status:** Partly superseded by ADR-011. The pipeline ran. None of the five finished issues took a back-edge. Every posted verdict was approve.
- **Date:** 2026-11-20

## Context

Something has to decide when stage 4 goes back to stage 3, when stage 6 goes back to stage 2 or 3, and when the run stops. I could use a model as a planner, a Python state machine in one job, or GitHub Actions jobs wired with `needs` and `if`.

The assignment already fixes the back-edges. Tests fail: retry implementation, and if they keep failing, look at the design again. A review that objects to the approach goes back to design. A review that objects to the code goes back to implementation. At most two review rounds. A person merges.

The default `GITHUB_TOKEN` on this repo is read-only. A job that pushes has to set `contents: write` on itself. If one job both reviews and pushes, the reviewer has a token that can push. That fights ADR-008.

`ci-workflow.yml` already has the project's test matrix. I should not rebuild that matrix. The workflow opens a pull request and then reads the check the existing workflow produces.

## Decision

The workflow file is the controller. Jobs are `gate`, `analyst`, `builder`, `release` and `review`. The builder job runs the implementer, the tester and pytest, and it loops inside the job up to the budget in ADR-009. Review rounds are two copies of the review path (`review`, and `review_again` when the verdict asks for another round). A model does not pick the next job.

A job starts only when the previous stage's check file says `pass`. The analyst does not get to say stage 1 is done. The builder does not get to say pytest is done. The rules are in ADR-007.

Who sends work backward:

| Observation | Who notices | Where it goes |
| --- | --- | --- |
| Spec or design script failed | The analyst job, after one regeneration | The run stops. The artifact says which check failed. |
| `import tinydb` failed | The builder job | The run stops. No pull request. |
| pytest failed, retries left | The builder job | The implementer, with the pytest log. |
| pytest failed, retries spent | The builder job | The analyst once, then one more build. Then stop. |
| `verdict: code` | The review job's script | The builder job, if this is round 1. |
| `verdict: approach` | The review job's script | The analyst job, if this is round 1. |
| `verdict: approve`, or round 2 is done | The review job's script | Stop. The pull request stays open. |

The controller is not allowed to merge, close the pull request, or delete the branch.

## Alternatives considered

A planner model that picks the next stage. It can skip the reviewer, treat a failed pytest as a pass, or keep going after two review rounds. The stages are a known graph. Paying a model to rediscover it also gives the issue text a place to add a new edge.

One Python process for every stage, including review and push. Loops are easier to write. The process that can push is then the process that reviews, so reviewer independence is only a line in the prompt.

Chained workflows that trigger each other with `workflow_dispatch`. Each hop shows up as its own run, which is easier to debug, and each hop has to re-check the actor and find the artifacts again. The back-edge budget would be split across runs and would be easier to blow past.

## Consequences

The YAML repeats the review job, because Actions has no loop. That repetition is the record of "at most two rounds." I can see both rounds without opening a trace.

A bug in an `if` can skip a stage. Each job exits non-zero when its check file is missing or says `fail`, and `needs` will not start the next job.

The builder job holds both the implementer and the tester so a pytest retry does not need a new Actions job. They are still separate processes, with the hand-off from ADR-003. The job permission stays `contents: read`. Push waits for the release job.
