# ADR-003: Hand off artifacts, and withhold the builder's reasoning

- **Status:** Accepted. The hand-off was used on the finished runs. Hidden tests were run by a person afterwards. On issue #2 the reviewer approved a diff that does not fix the issue.
- **Date:** 2026-11-20

## Context

Each stage needs enough to do its work, and no more. The assignment is specific about the reviewer: it sees the issue, the diff, and the repo at the pull request head. It may run the code. It does not see the implementer's conversation. The tester has the same pressure one step earlier. A grading copy of the hidden tests lives at `experiment/hidden_tests/`, and the issue texts live at `experiment/issues/`, because that is the submission layout. Those directories are not a hand-off. Every file tool refuses a path under `experiment/`.

Assignment 2's `ARCHITECTURE.md` describes Python-Markdown. This fork is TinyDB at `edff96a`. Giving the analyst that document would name `markdown.preprocessors` and `Registry`, which are not in this tree.

Anyone can write an issue. The body is data, not instructions. ADR-009 says how that is enforced. This record says what is included.

## Decision

| Receiver | Receives | Does not receive |
| --- | --- | --- |
| Analyst | Issue title and body inside an `untrusted` fence. `ARCHITECTURE.md` at the repo root. A read-only checkout of `master`. | Hidden tests. The reviewer's later notes, on the first pass. Any secret. |
| Implementer | `spec.md`, `design.md`, write access to the checkout, and on a retry the pytest traceback or the review's file list. | The tester's prompt, the reviewer's conversation, hidden tests. |
| Tester | `spec.md`, `design.md`, `diff.patch`, and on a retry the pytest log. | The implementer's messages. Write access outside `tests/`. |
| Release script | Branch name, the spec's first heading, a `test_report.md` whose recorded exit code is 0. | A model, so it cannot treat a failure as a pass. |
| Reviewer | The issue title and body, `git diff` of the pull request against `master`, a fresh checkout of the pull request head. Permission for the workflow to run pytest. | `spec.md`, `design.md`, `test_report.md`, builder logs, the analyst's messages, hidden tests. |

`spec.md` and `design.md` are Actions artifacts. They are not committed. If they were committed, the reviewer's checkout of the pull request head would include them, and the restriction above would be a prompt line the model can ignore by opening the file.

The tester is allowed to see `spec.md` because its job is to write one test per acceptance criterion. The reviewer is not, because the assignment says its inputs are the issue and the diff. The issue is the request. The spec is the analyst's reading of it.

## Alternatives considered

Commit `spec.md` and `design.md` on the branch so a restarted job can read them without artifacts. A person reading the pull request would see the spec next to the code, and the reviewer could read the analyst's plan. ADR-004 stores those files as artifacts instead. A new run starts over.

Give every agent the full conversation so far. Debugging would be easier. The tester and the reviewer would also inherit the implementer's justification and would tend to agree with it.

Give the analyst the Assignment 2 architecture document plus this tree. That document is the wrong system. The root `ARCHITECTURE.md` in this fork is the replacement, written from `database.py`, `table.py` and `storages.py` at `edff96a`.

## Consequences

The reviewer can still open tests the tester committed, because those tests are part of the diff. The assignment says the reviewer sees the diff. It can notice a test that does not match the issue. It cannot see the hidden tests, so a pass on the pull request is not a pass on `experiment/hidden_tests/`.

On a review retry, the implementer sees a file list and the verdict, not a paragraph about how to rewrite the function. The return edge names the place that is wrong. A long note would put the reviewer in the implementer's seat.

If `design.md` names the wrong file, the implementer will follow it. The stage 2 script checks that the named file and function exist. It does not check that they are the right place to edit. That call is the analyst's. A wrong plan comes back through `verdict: approach`.
