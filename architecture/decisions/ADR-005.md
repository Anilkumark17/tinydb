# ADR-005: File tools for the models, `gh` for the release script

- **Status:** Partly superseded by ADR-012 and ADR-021. File tools were the only model tools. Rewriting `tinydb/table.py` with `write_file` was cut off on [run 44889133139](https://github.com/Anilkumark17/tinydb/actions/runs/44889133139).
- **Date:** 2026-11-20

## Context

The models need to read TinyDB and write a small patch. Release needs to push and open a pull request. GitHub offers the `gh` CLI, the REST API and the GitHub MCP server. This runner lives in GitHub Actions, which already has `GITHUB_TOKEN` and a checkout.

The default workflow token is read. A job that does not ask for more cannot push. That default only helps if each job's token is declared on that job and the model process does not inherit it. Environment variables are inherited by every command in the step.

Anyone can open an issue. A general shell would let the issue text ask the model to `curl` the Gemini key or push to `msiemens/tinydb`. The workflow may write only to `Anilkumark17/tinydb`.

## Decision

Models get a fixed tool list inside the runner. No shell. No MCP server.

| Role | Tools | Token in that process |
| --- | --- | --- |
| Analyst | list directory, read file | none |
| Implementer | list directory, read file, write file, under the checkout, refusing paths outside it | none |
| Tester | list directory, read file, write file under `tests/` only | none |
| Reviewer | list directory, read file, `run_tests` (no arguments; the runner runs the fixed `uv run pytest` command and returns the summary and failing node ids) | none |
| Release | `git push` of `autose/issue-<n>` and `gh pr create --base master --body-file` | `contents: write`, `pull-requests: write`, `issues: write` on the release job only |

The runner reads `GEMINI_API_KEY` from the secret. The key is not put in the prompt, the artifact, or a tool argument. The model asks the runner to call the API. The model does not see the key.

I use `gh` rather than a hand-written REST client because release is one pull request and one comment. The MCP server would add another network service and a tool list wide enough to edit issues, labels and workflows. I don't need that.

The implementer cannot run pytest. The tester cannot edit `tinydb/`. Both limits are in the runner, not only in the prompt. Pytest is a workflow step so its exit code is the job's exit code.

The release script sets the remote to `Anilkumark17/tinydb`. It does not read a remote URL out of the issue body.

## Alternatives considered

Give every job `contents: write` and tell the reviewer not to push. The default token was set to read so a job has to opt in. A blanket write undoes that.

GitHub MCP for all roles. One server could serve issues, pull requests and files. It would also serve those operations to whichever role held the token. Five MCP permission profiles is more machinery than four file tools and one `gh` call.

Let the implementer run a shell. TinyDB's tests are `uv run pytest`, and a shell could run that. A shell can also run whatever the issue text names. The workflow step is the only pytest invocation.

## Consequences

A change that needs a new dependency cannot `pip install` it from the model. These five issues are changes to `Table`, and `pyproject.toml` already has the test tools. If a later issue needed a dependency, this ADR would have to be superseded. This is the right limit for this repo. It is a bad limit for a general coding agent.

The release job is the only job that can move refs. A bug in the release script is the only path to a bad push. The script pushes one branch name taken from the issue number, with `--base master`, and it does not call `gh pr merge`.

When the reviewer runs pytest, it uses the same `uv run pytest` as stage 4. It can check the tree at the pull request head. It cannot use a command taken from `review.md`.
